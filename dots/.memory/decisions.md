# Dotfiles Architecture Decisions (`dots/.memory/decisions.md`)

Active, canonical decisions for the `dots/` subtree. High-signal — read before
implementation. Scoped layer beneath repo-root
[`decisions.md`](file:///home/lowcache/.nix-config/.memory/decisions.md).

## D1 — Scoped memory lives at `dots/.memory`, never inside an app dir
Because each `dots/<app>/` is a whole-directory `mkOutOfStoreSymlink` into `~/.config`,
any file placed inside an app dir leaks into the live config (and into quickshell's QML
loader). `dots/` itself is not a symlink target, so the scoped `.memory/` and `.model/`
go there. Per-app notes use subdirs under `dots/.memory/`, not under the app dir.

## D2 — Independent history via `git subtree`, not submodule
The `dots/` tree must be trackable on its own history yet remain in the single nix-config
repo with no separate working repo and no submodule. `git subtree split/push/pull` gives a
derived, regenerable projection branch (`dots-history`) that can be published to a standalone
`dotfiles` remote and merged back, without moving any files — so `mkOutOfStoreSymlink` paths
are never disturbed. Submodules were rejected: they create a separate `.git`.

## D3 — Edit the palette, not generated theme outputs
The colorscheme is generated by `apply_theme.py` from a palette JSON
(`color-engine/themes/<active>.json`). Generated files (`Appearance.qml`, `colors.conf`,
kitty/starship configs) are overwritten on every apply. Color changes are made in the
palette JSON and re-applied; hand-edits to generated files are non-durable.

## D4 — Preserve hot-reload; no static Home-Manager dotfile outputs
Dotfiles are out-of-store symlinks specifically so edits are live without a rebuild. Do not
replace them with Home-Manager `text`/`source` outputs that would write static copies to
`~/.config`. Keep the out-of-store link to `dots/`.

## D5 — `amalgamation` and `petrified_spittoon` are the canonical theme templates
These two theme JSONs carry the full mapping structure the generator consumes
(`surfaces` / `accents` / `text` / `states` / `terminal`, with real `*_fixed_dim`,
`inverse_primary`, `*_container`, and M3 `error*` / `success*` roles). Now in
`dots/color-engine/themes/`. New themes are built by cloning one and re-coloring. The
other theme files (`amirage`, `bb`, `blackmeddle`, `horizon_neon`, `skumring`,
`soft_pastel`, `vivendi_tinted`) are unused/legacy — do not treat them as references.
A new theme is complete when every mapping value resolves to a defined palette key (no
dangling refs — see [[mistakes]] M1).

## D6 — Color engine is compositor-agnostic; lives at `dots/color-engine/`
`apply_theme.py`, `make_theme.py`, `check_theme.py`, and `themes/` were moved out of
`dots/illogical-impulse/scripts/` to `dots/color-engine/` (2026-06-17). The generator
drives ii/Hyprland, kitty, starship, AND niri/Noctalia — not ii-specific. A new symlink
`~/.config/color-engine` was added to `home/persist.nix`; **requires `make switch`**.
ii's nuitka build artifacts (`apply_theme.bin`, `apply_theme.dist/`) remain at
`dots/illogical-impulse/scripts/` — regenerable, not relocated.

## D7 — Callers outside `apply_theme.py` never name a theme explicitly
Any script invoking `apply_theme.py` must call it with **no theme argument**, deferring
to `masterTheme.jsonPath` in `~/.config/illogical-impulse/config.json`. Hardcoding a
theme name bypasses the configured active theme; passing a bare name (not a path) makes
`os.path.exists()` return False and silently no-ops. Both `switchwall.sh` call sites fixed
2026-06-17. This convention is what makes wallpaper-change hooks theme-agnostic.

## D8 — Quake terminal: niri spawns process only; kitty owns all window logic
For the niri quake drop-down terminal, niri's only role is `spawn`. Every window
operation — show, hide, position, size, orientation — is handled by kitty via
`quick-access-terminal` (wlr-layer-shell kitten) and kitty remote control. The compositor
never manages the quake window's lifecycle. This is the opposite of the Hyprland approach
(scratchpad/special-workspace). Attempts to manage floating window visibility through niri
(window-rules + move-window-to-workspace) spawned duplicates and were fragile. The old
`quake_toggle.sh` implementing that approach was deleted 2026-06-18.

## D9 — Quake keybind scheme: Mod+Return family, orientation-aware position toggle
Four orthogonal controls hung off `Mod+Return`; `Mod+Shift+Return` (position) is
orientation-aware — adapts to landscape or portrait — rather than having separate
keybind sets per orientation:
- `Mod+Return` — show/hide (`toggle-visibility`, preserves geometry)
- `Mod+Shift+Return` — position: top↔bottom (landscape) or left↔right (portrait)
- `Mod+Alt+Return` — size: normal↔full (fullscreen in any orientation, verified)
- `Mod+Ctrl+Return` — orientation: landscape↔portrait
State persisted per-axis in `$XDG_RUNTIME_DIR/kitty-quake.state` (4 fields: `orient`,
`pos_h`, `pos_v`, `size`). Each axis remembers its own side independently. A separate
keybind set for portrait-only was rejected as insufficient benefit for the cognitive load.
