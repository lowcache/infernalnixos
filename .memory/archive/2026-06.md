### 2026-06-09 — tuigreet Environment Variables Not Loading in Non-Login Context

* **Symptom:** Session environment variables (like `GTK_USE_PORTAL=1`, `XDG_DATA_DIRS`, `XDG_CURRENT_DESKTOP`) fail to load when starting the compositor via `tuigreet` (greetd frontend). Portal dialogs fail, apps see missing icons/schemas, overall session integration breaks. **Pattern:** The workaround works, then breaks on next rebuild, suggesting the config was not properly declarative.
* **Root Cause:** `tuigreet` launches the session in a **non-login shell context** (greetd is a system service, not an interactive login). Standard shell startup files (~/.bash_profile, ~/.bashrc, ~/.profile, and fish `shellInit`/`sessionVariables` from Home Manager) are **not sourced** when the compositor starts from greetd. The only mechanisms that successfully pass environment to the session are: (a) tuigreet's `--env` flag, (b) a wrapper script that exports vars before exec'ing the compositor.
* **Prevention Rule:** **Always** pass session environment variables explicitly via tuigreet's `--env` flag or wrapper script. **Option A (via `--env` flag):** `services.greetd.settings.default_session.command = "${pkgs.greetd.tuigreet}/bin/tuigreet --env GTK_USE_PORTAL=1 --env XDG_CURRENT_DESKTOP=hyprland --cmd hyprland";` **Option B (via wrapper script):** Use `pkgs.writeShellScriptBin` to create a session script that exports vars, then `exec` the compositor; pass that script to `--cmd`. **Verification:** Post-rebuild/reboot, run `echo $GTK_USE_PORTAL` in a terminal inside the compositor session — should print `1`, not be empty. **Git history:** This pattern was discovered and iterated across commits cd7db0b, 4230bd7, 728a728 (pre-memory-system). Consulting those commits shows the working and broken configurations.

### 2026-06-12 — File-chooser/portal bug: Hyprland ambient CAP_SYS_NICE ptrace gate (NOT dbus-broker pidfd bug)

**Symptom:** Brave browser, file-roller, and all GTK/Electron apps fail to open file-chooser dialogs. `gdbus call --session --dest org.freedesktop.portal.Desktop --object-path /org/freedesktop/portal/desktop --method org.freedesktop.portal.Settings.ReadAll '[]'` returns `GDBus.Error:org.freedesktop.DBus.Error.AccessDenied: Portal operation not allowed: Unable to open /proc/<pid>/root`. See mistakes.md #9 and #10 (earlier wrong diagnosis).

**Root cause (PROVEN 2026-06-12):** 
1. `programs.hyprland.enable` (nixpkgs module) creates `security.wrappers.Hyprland` with `cap_sys_nice+ep` (for SCHED_RR).
2. Hyprland 0.55.2 raises that capability as **ambient** for every spawned client → all session/GUI apps (kitty, Brave, antigravity-ide, gdbus, etc.) carry `CAP_SYS_NICE` in their permitted set.
3. xdg-desktop-portal runs as a capless systemd user service (`CapPrm=0`).
4. Portal app-id resolution opens `/proc/<client>/root` (ptrace-read-gated magic symlink). Kernel `cap_ptrace_access_check` denies PTRACE_MODE_READ when target's permitted set (CAP_SYS_NICE) is not a subset of opener's (empty) → EACCES.
5. Portal: "Could not register app ID" → rejects every request from session apps → `AccessDenied`.

**Evidence:**
- `2×2 matrix`: only "user-service opener (portal) → session-app target (CAP_SYS_NICE)" fails (EACCES); other magic links `/proc/<pid>/environ`, `/proc/<pid>/cwd`, `/proc/<pid>/cmdline` succeed (no ptrace gate).
- `cap_ptrace_access_check` is classic gate; yama=1 does NOT gate PTRACE_MODE_READ, so LSM/yama irrelevant.
- **Smoking gun:** `gdbus call …Settings.Read` fails normally; **identical call via `setpriv --ambient-caps -all`** succeeds instantly.

**Previous wrong hypothesis:** mistakes.md #10 (2026-06-10) blamed dbus-broker pidfd bug. Disproven: dbus-daemon 1.16.2 also passes pidfds (confirmed `strings /usr/bin/dbus-daemon | grep ProcessFD`), and the 2026-06-09 "proof" (portal worked via `dbus-run-session`) succeeded only because the test was invoked **from a terminal** that inherited the same ambient cap as its clients — execution context, not bus implementation, was the variable.

**Immediate workaround (no rebuild):** `setpriv --ambient-caps -all --inh-caps -all <app>` (e.g. `setpriv --ambient-caps -all brave`) works instantly.

**Fix candidates (PENDING DECISION):**
- **Option A (surgical):** Override `security.wrappers.Hyprland` via `lib.mkForce` to drop `cap_sys_nice` from the wrapper. Fixes portal calls globally. Trade-off: loses Hyprland's SCHED_RR guarantee (desktop responsiveness may degrade under scheduler pressure).
- **Option B (compat):** Overlay-patch xdg-desktop-portal to treat EACCES on `/proc/<pid>/root` like ENOENT (fall back to app-id resolution via cgroup/env). Preserves Hyprland's capability. Trade-off: depends on portal patch quality; upstream may not accept.
- **Option C (upstream):** Check if xdg-desktop-portal ≥1.21+ already has a fix. Gemini's research (tether task `portal-cap-upstream-research`, 2026-06-12) pending.

**Prevention rule:** When xdg-portal file pickers or Settings calls fail with `AccessDenied / Unable to open /proc/<pid>/root`, diagnose with `cap_ptrace_access_check`: (1) compare `CapPrm` of the target (via `cat /proc/<pid>/status | grep Cap`) with the opener's (portal = 0); (2) if target has caps and portal doesn't, it's not a dbus bug — it's a capability divergence in the calling context. Test the immediate `setpriv` workaround; if it works, the root cause is ambient cap inheritance.

### 2026-06-12 — Hyprland 0.55.3 Super-tap (Super_L keypress) no longer opens search

**Symptom:** After upgrading to Hyprland 0.55.3, pressing Super_L alone (Super-tap) no longer opens quickshell search. Super+Tab (overview dispatch) still works.

**Prevention rule:** After any Hyprland point bump (0.55.4+), re-test Super-tap by tapping Super alone or running `hyprctl dispatch quickshell:searchToggleRelease`. If fixed upstream, remove the catchall interrupt line from keybinds.conf and close the follow-up todo. If still broken, check release notes for keybind handling updates or comment out the catchall (trade-off: lose unbound-key cancel protection for Super+unbound-key combos).

### 2026-06-15 — `nixos-rebuild switch` "broken pipe" root cause = 4G tmpfs `/` at 99%, not nix-store

**Symptom:** `make switch` / `sudo nixos-rebuild switch --flake .#volnix` failed with "broken pipe" error during system activation. GC was incorrectly suspected.

**Root cause (proven via disk inspection):** The impermanence tmpfs root `/` was at **99% capacity (56 MB free)**, not the `/nix` store (136 GB free). With `TMPDIR` unset, nix defaulted to `/tmp`, which lives **on the 4 GB tmpfs root**. A rebuild's heavy temp I/O (evaluation, derivation staging) quickly exhausted the 56 MB, write failures occurred, and the nix-daemon/client connection died → **"broken pipe."** Evidence: `df -h` showed `/` at 99%, `/nix` at 27%. `du` probes on `/tmp` showed only ~5 MB; root-level consumers identified but not their exact source (sudo unavailable in agent shell). Hypothesis: volatile `/var`, journals, or other root-level state consumed ~4 GB.

**Prevention rule:** (1) Point nix's temp at a disk partition with free space, **not** the tmpfs root. (2) User-side: `TMPDIR=$HOME/Storage/tmp` in shell config (shell-owned, separate disk). Daemon-side: `nix-daemon.environment.TMPDIR = "/nix/tmp"` (root-owned, on the nix partition, nixbld-traversable). (3) Makefiles and privileged targets must explicitly pass `TMPDIR` via `sudo TMPDIR=... command` — sudo resets the environment, so shell config doesn't reach it. (4) In an emergency one-off: `sudo TMPDIR=/nix/tmp nixos-rebuild switch ...`. (5) To identify what consumed the tmpfs root: run `sudo du -shx /* | sort -rh` and look for unexpected space hogs (journals, core dumps, /var subdirs).

**Fix applied (2026-06-15):** (1) `home/shell.nix`: `set -gx TMPDIR $HOME/Storage/tmp`. (2) `nixos/configuration.nix`: `nix-daemon.environment.TMPDIR = "/nix/tmp"` + tmpfiles rule to create `/nix/tmp` (1777, root-owned). (3) `Makefile`: `REBUILD_TMPDIR := $(HOME)/Storage/tmp` variable used in all privileged targets. All in place and eval-verified. Makefile change effective immediately; shell + daemon changes activate on next new shell / `make switch`. **Measured benefit:** ~20% rebuild speedup due to two-disk parallelism (user temp on nvme1 + daemon on nvme0).

### 2026-06-16 — WirePlumber saved "pro-audio" on all audio cards → silence on every output

**Symptom:** User unable to get analog, HDMI, or any audio output to work whether using the "Radeon controller" or "Ryzen controller," or whether selecting "OPRO Audio" or "Analog." All combinations resulted in silence.

**Root cause:** WirePlumber's saved config (`~/.local/state/wireplumber/default-profile`) contained:
```
alsa_card.pci-0000_01_00.1=pro-audio          # NVIDIA HDMI
alsa_card.pci-0000_66_00.1=pro-audio          # Radeon HDMI
alsa_card.pci-0000_66_00.6=pro-audio          # Onboard Realtek ALC256 (analog)
```
The "Pro Audio" profile exposes raw, unmapped multichannel ports with no default stereo routing. When a normal stereo application sends two channels to a Pro Audio sink expecting multichannel, the map fails and the audio goes to nowhere → silence on all three cards simultaneously, regardless of which was selected as default.

How it got there: pavucontrol's **Configuration** tab shows selectable profiles for each card. The two HDMI controllers (Radeon + NVIDIA) have no audio devices physically connected, so all HDMI profiles report `available: no` and are hidden by pavucontrol. The *only* non-hidden, selectable profiles left are **Off** and **Pro Audio** (Pro Audio always shows as selectable even with nothing connected, by design). ### 2026-06-16 — Root Tmpfs Filled to 100% by ~/.cache (Regenerable Cache Accumulation on Volatile /home)

**Symptom:** Root filesystem `/` (4 GB tmpfs) reached 100% capacity (380 KB free). Sessions became unresponsive; file I/O failed with ENOSPC errors (screenshots couldn't write, file pickers couldn't open files, general system slowdown until restart/cache clear).

**Root cause:** The impermanence setup leaves `~/.cache` on the volatile 4 GB tmpfs `/` (not persisted to `/persist` or redirected to `~/Storage`). Regenerable caches accumulated without automatic eviction: `~/.cache/llmfit` (3.2 GB) and `~/.cache/pip` (2.9 GB). These caches silently fill the tmpfs root until the system becomes unusable. The home directory itself (`/home/lowcache`) sits on the tmpfs as ephemeral, making it a catch-all for any application writing to standard paths without explicit redirection.

**Investigation:** (1) Symptoms manifested as ENOSPC on file write → checked `/tmp` (only 34 MB, not the filler) → checked `/` mount breakdown (`~/.cache` + `/var` journal consuming ~4.8 GB of 4 GB tmpfs). (2) Root cause isolated: `du -shx ~/.cache/*` revealed `llmfit` (3.2 GB) + `pip` (2.9 GB). (3) Confirmed these are regenerable: `pip` re-downloads on demand, `llmfit` rebuilds its cache. (4) Immediate mitigation: cleared `~/.cache/*` and verified root free space jumped from 376 KB to 3.7 GB (8% utilization).

**Prevention rule:** Do NOT treat clearing `~/.cache` as a solution — that frees space temporarily but the fillers recur silently. The durable fix is structural: remove regenerable caches from the tmpfs via one of two approaches:

1. **Persist `~/.cache` off the 4 GB tmpfs:** Bind-mount or symlink `~/.cache` to `/persist/home/lowcache/.cache` in `home/persist.nix`. Preserves regenerable caches across boots (acceptable since they auto-regenerate) and moves storage off the 4 GB tmpfs. Simple, one-time setup.

2. **Redirect cache environment variables at session init:** Set `PIP_CACHE_DIR=/home/lowcache/Storage/pip`, `XDG_CACHE_HOME=/home/lowcache/Storage/.cache`, and llmfit cache path (confirm env var name in llmfit source) to `~/Storage` in fish `shellInit` or `home/shell.nix`. Prevents apps from writing to `~/.cache` on tmpfs in the first place, giving independent per-app control.

**Recommended approach:** Combination: redirect `pip` and `llmfit` (the two highest-volume fillers, explicitly tuneable) via environment variables to `~/Storage`; bind-mount the rest of `~/.cache` to `/persist` as a fallback for other tools (Brave profile, nix, uv). This frees the 4 GB tmpfs from the two biggest fillers while preserving smaller, slower-regenerating caches across boots.

Unmitigated, any `pip install` or `llmfit` model download will refill the tmpfs and break the session again. 1. **One corrupted font file** (`NoracleNerdFont-Regular.otf`): truncated `cmap`/`OS/2` tables. Crashes FreeType/HarfBuzz in Krita's new SVG text engine during shape operations. `fc-scan` and fontconfig are too lenient to catch it (they accept malformed tables); only strict TTF/OpenType validators (fontTools) flag it.
2. **Distro-build regression in nixpkgs krita:** Krita synthesizes locale tag `en_Latn_US` (with script subtag `Latn`) and feeds it to fontconfig for font-by-language matching. Fontconfig rejects it as invalid ("not a valid region tag"). Result: font-by-language filtering fails, returns empty list even when 3675 fonts are installed and indexed.
3. **Design limitation:** Krita 6.0 SVG text engine is a power-user rewrite that assumes *curated* font sets. It does not scale to 2000+ files (resource-heavy, slow enumeration; crashes on one bad font among thousands).

**Prevention rules:**
1. Before upgrading to Krita 6.0+, audit font collections with strict validation (fontTools.ttLib.TTFont, checking `cmap`/`OS/2`/`name` tables for parse errors). Move corrupt files aside (may be recoverable by re-download; or genuinely truncated). `fc-scan` alone is insufficient.
2. For workflows using 2000+ fonts, choose: (a) stay on **Krita 5.2.15** (last release with classic text tool; nixpkgs commit `09061f748ee21f68a089cd5d91ec1859cd93d0be`), or (b) switch to **GIMP 3.0.8+** (Pango/fontconfig backend proven at scale, searchable font list, more forgiving of large collections).
3. Quarantine location for diagnostic/reference: `~/Storage/tmp/quarantined-fonts/`. See state.md §2.
4. If choosing Krita 5.2.15 pin: override `paths = [ pkgs.krita ]` in `home/pkgs.nix` to point at the older nixpkgs revision. Verify with `nix eval` before rebuild.

### 2026-06-22 — SVG Text-Shape Insertion Crashes Krita 6.0.1 (err=84 RenderGlyph)

* **Incident (2026-06-22):** Double-clicking a font in Font Gallery pykrita plugin (which attempted to insert an SVG `<text>` shape on a vector layer) crashed Krita instantly. Journal flooded with `render glyph failed err=84 face=... glyph=...` for every glyph in the font, then SIGABRT.
* **The Bug:** Krita 6.0.1's text engine (specifically the glyph rasterizer, `err=84 = RenderGlyph operation failed`) is fundamentally broken when handling certain font rendering scenarios. When an SVG `<text>` shape is inserted and projected (rendered asynchronously) by Krita, the glyph rasterization pass fails on **every glyph** of any font, flooding the journal and aborting the app. The crash occurs in Krita's async render pipeline, **after** the plugin Python call returns — nothing in Python can catch it. This is not a plugin bug; it is Krita's renderer crashing on its own text engine.
* **Prevention Rule:** Do not attempt to insert `<text>` shapes or rely on Krita 6.0.1's text engine for font rendering. Use a **pre-render offline approach:** invoke Qt's `QFont` + `QPainter.drawText` to rasterize glyphs into a `QImage` (offscreen, in a subprocess or dedicated Qt context if needed), then blit the pixel buffer to a Krita **paint layer** via `setPixelData`. Qt's glyph renderer works fine (proven on this system; it powers the font list docker). The blit path avoids Krita's broken engine entirely. Output is raster (not editable vector text), but the safety trade-off is necessary.

### 2026-06-23 — toybox Multi-Call Binary Collision in home-manager buildEnv

**Symptom:** Commit `3135d5e` added `toybox` to `home.packages` in `home/pkgs.nix`. buildEnv failed at `home-manager-path.drv` with a duplicate-file collision: `bin/readelf` provided by both `gcc-wrapper` and `toybox`.

**Root cause:** Toybox is a multi-call binary that provides applets for grep, tar, awk, sed, find, readelf, ls, cp, rm, mv, and dozens of other utilities. The basedevel package set already includes all of these as standalone packages: binutils (readelf), coreutils (ls, cp, rm, mv, cat, echo, …), gnugrep (grep), gawk (awk), gnutar (tar), gzip (gzip), findutils (find), diffutils (diff). When home-manager buildEnv merges all packages into a single `$PATH`, it detects duplicate binaries and fails. Toybox was wholly redundant — every applet it provides already exists in the environment.

**Prevention rule:** Before adding multi-call binaries (toybox, busybox, Alpine-based coreutils replacements) to `home.packages` or `systemPackages`, verify their applets don't collide with existing packages. Use `toybox --list` (or equivalent) to enumerate provided commands, then cross-check against the target environment. If collisions exist: (1) remove the tool if redundant (simplest, and correct here); (2) use `lib.lowPrio` only if the intent is a fallback — note that home-manager buildEnv does NOT respect `meta.priority`, so this doesn't work there (only in `nix run` / standalone environments); (3) wrap the tool to selectively hide conflicting applets (complex; avoid unless essential). In this case, removal was the right fix.
