### 2026-06-23 — xcb-Only AppImage Qt Plugin Failure on Pure Wayland (niri)

* **Incident (2026-06-23):** FireAlpaca 2.16.0 AppImage (125 MB) failed to launch with `qt.qpa.plugin: Could not find the Qt platform plugin`. Global environment had `QT_QPA_PLATFORM=wayland`, but the AppImage bundles only Qt's `xcb` plugin ("Available platform plugins are: xcb"). niri is pure Wayland with no built-in X11 support.
* **Root cause:** Three compounding factors: (1) FireAlpaca's bundled Qt libs only include the `xcb` plugin, not wayland; (2) the global `QT_QPA_PLATFORM=wayland` environment variable instructed Qt to use wayland (not present in bundle); (3) xwayland-satellite was installed but not running, so even forcing `xcb` had no X server to connect to.
* **Recovery:** Started `xwayland-satellite :0` manually; launched with `DISPLAY=:0 QT_QPA_PLATFORM=xcb`. Qt initialized cleanly, app proceeded past plugin init. Confirmed reproducible.
* **Prevention Rule:** (1) On pure Wayland compositors (niri, sway, etc.) with xcb-only AppImages/legacy apps, start an X11 bridge early. `xwayland-satellite :0` is the lightweight choice; add `spawn-at-startup "xwayland-satellite" ":0"` to the compositor config (niri) or session startup script. (2) For users of such apps, export `DISPLAY=:0 QT_QPA_PLATFORM=xcb` in a launcher wrapper or alias. (3) This applies to **any** bundled Qt app that ships only `xcb` plugin, and to Flatpak Qt5 apps which use the old xcb backend.

### 2026-06-25 — Quake Terminal Script Aborts on Cold Start (set -e + missing socket query)

**Symptom:** `Mod+Return` keybind "does nothing" — terminal does not launch on first keypress after boot. Only works if terminal is already running (toggle hide/show). Appears to be a regression, but keybind config is valid and reaches the script.

**Root cause:** `sock()` helper in `dots/niri/scripts/quake.sh` runs `ls -t $SOCK_GLOB 2>/dev/null | head -n1` to find the kitty listen socket. When no socket exists (terminal not yet running), `ls` exits 2 (no match). Under the script's `set -euo pipefail`, this causes the bare assignment `s=$(sock)` to abort the entire script via `set -e` before it ever reaches `launch`. On this system with tmpfs root and `/run` wiped each boot, the socket is always gone at startup → cold-start path always fails.

**Prevention:** Any command-substitution query that can legitimately return "nothing" (glob `ls`, `grep`, `pgrep`, `find`) must be made non-fatal in a `set -euo pipefail` script. Use `|| true` at the call site or in the function definition. The "no result" is a valid answer, not an error.

**Fix applied (2026-06-25):** `sock()` now ends in `|| true`. Verified: cold launch, toggle, geometry changes all work with state persisting. No rebuild needed (live script symlinks to dots source via `/persist`).

### 2026-06-26 — memd global-root: Antigravity mis-attribution via substring-count assumption

**Symptom:** Antigravity conversations were silently attributed to the global memory root (`$HOME`) instead of their actual project, causing them to be skipped during curator distill (global is inbox-only). 1 ag-dbs entry mis-cached, causing the first tether review conversation to lose its project attribution.

**Root cause:** `project_ag_dbs` constructs its own `roots` list independently, and `_ag_assign_project` assigns conversations to whichever root their payloads mention most (substring count). The global root's path (`/home/lowcache`) is a substring of every home path (e.g., `~/.nix-config`, `~/CodeRepo/*`, etc.), so it won every attribution by default. The leak was fixed in `find_project` and `transcript_files` (early returns for global), but `project_ag_dbs` was never hardened — a coverage failure, not an ignorance failure.

**Prevention rule:** When introducing a value that violates an invariant (a path that's a prefix of all others), enumerate EVERY site that independently rebuilds a list depending on that invariant. Don't patch instances you've closely read and skip parallel code paths. Run a systematic grep sweep before declaring done, or request independent review.

### 2026-07-06 — Git Dubious Ownership Guard Blocks Privileged Rebuilds

**Symptom:** `make switch-detached` fails with `error: getting the HEAD of the Git tree '/home/lowcache/.nix-config' ... exit code 254` (shown in `journalctl -u nixos-switch`). The systemd unit runs nixos-rebuild as root.

**Root cause:** nix's git fetcher shells out to `git` to fetch the flake input `git+file:///home/lowcache/.nix-config`. The repo is owned by `lowcache:lowcache` (uid 1001). Since git 2.35+, the `dubious-ownership` guard rejects access from a different uid (root) unless the repo is whitelisted. nixos-rebuild-ng never reads `SUDO_UID` or `SUDO_USER` environment variables, so the Makefile's `--setenv=SUDO_UID` hack does nothing.

**Prevention rule:** For locally-owned git repos that will be fetched by root-running nix, whitelist them in system-level git config via `programs.git.config.safe.directory` in `nixos/configuration.nix`. The setting lands in `/etc/gitconfig` (declaratively, survives tmpfs root) and applies to all git invocations by root. Example: `safe.directory = [ "/persist/home/lowcache/.nix-config" "/home/lowcache/.nix-config" ];` (both symlink variants, in case). After applying (via plain `make switch` as user), `make switch-detached` works permanently.

**Verification (2026-07-06):** `nix eval .#nixosConfigurations.volnix.config.environment.etc."gitconfig".text` confirms entries land in generated config. Build verification pending (kicked off background, may have been interrupted).

### 2026-07-09 — Phase 5 Tor Option Casing (SocksPort vs SOCKSPort)

**Symptom:** `nix flake check` failed with reference to unknown/wrong Tor settings key.

**Root cause:** Task file (P5-T1 spec) specified `SocksPort`, but the nixpkgs tor module declares the option as `SOCKSPort` (caps). The wrong key fell through to the freeform string type in the schema, which accepted it without error during initial editing but failed schema validation during the eval gate.

**Prevention rule:** When referencing nixpkgs module options, always verify the exact casing against the module definition (`grep -n 'SOCKSPort\|SocksPort' $(nix eval --raw nixpkgs#path)/nixos/modules/services/security/tor.nix`) rather than relying on task specification or memory. Option names are case-sensitive; a missing capital letter silently breaks schema validation.

### 2026-07-12 — Formatter Hook Eats Unreferenced Let-Bindings During Multi-Step Edits

**Symptom:** During multi-step Nix edits that add a new let-binding in step 1 and reference it in step 2, the PostToolUse hook runs a deadnix-style cleanup after step 1, silently deleting the binding as "unused" before step 2 can reference it. Affected `flake.nix` edits that added `system` and `pkgs` let-bindings then referenced them in outputs.

**Root cause:** User has a PostToolUse hook configured (via settings.json or home-manager) that runs deadnix to remove unused declarations after each Edit tool call. In a multi-step workflow, intermediate AST states are legitimate (binding created, then referenced in the next edit). The hook fires after step 1, sees the binding is unreferenced, and removes it — step 2 then fails to find the binding or the binding is gone.

**Prevention rule:** When making stepwise Nix edits, either (1) combine binding-creation and binding-reference into a single Edit call if possible (creates both, references both in same pass), (2) temporarily disable the cleanup hook for the series, (3) expect bindings to be eaten and re-add them as needed, or (4) request independent review before the cleanup pass. The hook itself is useful — it's the user's awareness of the interaction that matters. After each multi-step edit sequence, verify that all let-bindings and their references landed correctly (a quick scan of the touched regions).

### 2026-07-14 — Krita G'MIC buildEnv Duplicate Plugin Conflict

**Symptom:** `make switch` failed with `pkgs.buildEnv error: two given paths contain a conflicting subpath` when trying to add a standalone patched G'MIC plugin. Two store paths both contained `krita_gmic_qt.so`:
- `/nix/store/34iqj5…-krita/lib/kritaplugins/krita_gmic_qt.so` (bundled in krita via symlinkJoin)
- `/nix/store/vx8znad…-krita-plugin-gmic-3.7.4.1/lib/kritaplugins/krita_gmic_qt.so` (standalone patched plugin)

**Root cause:** The nixpkgs `krita` package is a `symlinkJoin` of `krita-unwrapped` + `binaryPlugins` (default `[ krita-plugin-gmic ]`). The G'MIC plugin is already bundled inside. Adding a second standalone `krita-plugin-gmic-patched` to home.packages created a duplicate — buildEnv deduped them silently when both resolved to the same store path (unpatched), but failed when the standalone one was a different derivation (patched). The fix was NOT to add a second plugin, but to override **which** gmic the krita wrapper bundles: `krita-wrapped` overrides `pkgs.krita.override { binaryPlugins = [ krita-plugin-gmic-patched ]; }`, so there's exactly one (patched) copy.

**Prevention rule:** When patching a plugin bundled inside a larger package via `symlinkJoin`, do NOT add the patched plugin as a standalone entry to home.packages. Instead, override the parent package to use the patched version internally, so there's no duplication. Check the parent's derivation (look for `symlinkJoin`, `binaryPlugins`, or similar collection logic) to find the right override point. `nix-diff` or `nix flake show --impure` can help identify what's already bundled.

### 2026-07-28 — systemd-run Transient Units: Minimal DefaultEnvironment PATH

**Symptom:** `make switch-detached` (run via `sudo systemd-run …`) failed with `error: getting the HEAD of the Git tree '/persist/home/lowcache/.nix-config' failed with exit code 254:` followed by empty stderr.

**Root cause:** Transient systemd units inherit the systemd manager's DefaultEnvironment `PATH`, which on this system is only `dosfstools/mtools/e2fsprogs/util-linux/systemd` — no `git`, no `/run/current-system/sw/bin`. Lix's flake fetcher (`nix flake metadata git+file://…`) needs to invoke `git` for input fetches; when git is not on PATH, lix cannot spawn the subprocess and surfaces the spawn failure as "exit code 254" with empty output (not a git error — a system call failure). Plain `sudo make switch` works because sudo passes the user's full PATH through.

**Prevention rule:** Any `systemd-run` or `systemd-run --scope` invocation that ends up calling nix/lix flake operations (which internally invoke `git`) must have an explicit PATH containing `/run/current-system/sw/bin` and `/run/wrappers/bin`. Pass `--setenv=PATH=/run/current-system/sw/bin:/run/wrappers/bin` to `systemd-run`. Symptom if missing: "exit code 254" with empty stderr from a lix subprocess.

**Also beware:** Plain errors like "git not found" from nix/lix are surfaced as exit code 254 with no error message — this is a lix quirk for spawn failures. If you see that exit code, the culprit is almost always a missing binary on PATH inside the transient unit's environment.

### 2026-07-28 — pytest >= 9.1: PytestRemovedIn10Warning Escalated to Hard Error

**Symptom:** `python3.14-pandas-stubs` 3.0.3 check phase failed during test collection with 8 errors; all errors were `PytestRemovedIn10Warning` re-raised as exceptions.

**Root cause:** pytest >= 9.1.1 promotes `PytestRemovedIn10Warning` (a deprecation notice in pytest < 9.1) to a hard error at collection time. The package `python3.14-pandas-stubs` sets `filterwarnings = error` in `pyproject.toml`, which turns all warnings (including the promoted one) into exceptions. The package's test suite passes generators to `pytest.parametrize` (which pytest now warns about), so all 8 collection errors abort the build before any tests run. Transitive dependency of `markitdown`/`pdfplumber` in home-manager path, causing full system build failures.

**Prevention rule:** When a Python package build breaks at check collection (not at test execution) in pytest >= 9.1, inspect the error for `PytestRemovedIn10Warning`. If present, apply an overlay to downgrade that specific warning via `PYTEST_ADDOPTS="-W ignore::pytest.PytestRemovedIn10Warning"`, piped into the build environment as `preCheck` or in nixpkgs' `pytestCheckHook`. Do not disable `doCheck` (that strips check inputs and breaks unconditional import checks). Verify the fix by confirming pytest runs full suite and reports pass count (e.g., "3151 passed, 5 skipped").

**Upstream tracking:** Once pytest ships a new major or the warnings are promoted to errors in future releases, update the overlay's warning filter accordingly. Revert the overlay when nixpkgs ships a patch to the package that handles the new warning.
